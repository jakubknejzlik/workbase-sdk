> Instance deployment workflows are omitted. Configure and review deployment automation separately before remote use.

# Standalone Workbase instance

Generated by `workbase init` (alias: `workbase-mcp init`) or the configuration MCP's
`bootstrap_instance`. The config id is `{{INSTANCE_ID}}`; the MCP selector is
`{{INSTANCE_SELECTOR}}`. Start with no application entities, permissions or policies.
The three SDK dependencies use the exact release version {{SDK_VERSION}}.
The generic browser console is already packaged in plugins.

Bootstrap writes files only, preserves conflicts and reports every file. It validates
ID, target and paths before writing. It never installs or contacts a service.
Accepted calls are audited in `proposals/log.jsonl`; rejected inputs are not audited.
Use a destination inside the configuration server's root; symlinks are rejected.

Use Bun 1.4.3 and Node 22.13+ (SQLite support). Run from this repository root:

```sh
bun install
bunx --no-install sst install
bun run migrate:initial # once, only when migrations has no SQL
bun run typecheck
bun run check:migrations
```

Typecheck checks instance and installed SDK sources strictly; it counts and excludes
diagnostics inside downloaded SST platform implementations (skipLibCheck only
handles declarations). Commit the lockfile, config, history, SQL, entrypoints and
workflows. Restart the configuration MCP after installation. The SDK getting-started
guide covers login and MCP registration. See CLAUDE.md for the branch/MCP/PR guide.

## Local development

Copy `.dev.vars.example` to `.dev.vars` and set a private stable secret using
`openssl rand -hex 32`. Stop the Worker before applying local migrations:

```sh
bun run migrate:local
bun run migrate:plugins
bun run dev
```

Wrangler is local development only. It serves the installed console assets directly.
Without an EMAIL binding, retrieve the newest link from local D1 after requesting
login in the browser:

```sh
bunx --no-install wrangler d1 execute DB --local --persist-to .wrangler/state --command "SELECT body FROM email_outbox ORDER BY created_at DESC LIMIT 1"
```

Open that link on the same loopback origin. No password mode is enabled remotely.
Configuration and data MCP run as separate processes via `.mcp.json`. Supply
WORKBASE_TOKEN and WORKBASE_ORG_ID for the data process; it defaults to read-only.

## SST deployment and remote login

Copy `deploy.env.example` to `.env` and fill the operator inputs. There are no seeded
owners. WORKBASE_OWNER_EMAIL records the address you will use at the login page;
it is not a Worker binding or an authorization grant. Registration is open and
an authenticated user can create an organization and become its owner. Review
that registration policy before allowing public traffic.

Supply CLOUDFLARE_DEFAULT_ACCOUNT_ID, CLOUDFLARE_API_TOKEN, a stable
BETTER_AUTH_SECRET (at least 32 characters), and WORKBASE_RESOURCE_PREFIX
(lowercase DNS-style name, <=63 characters). Keep app name, prefix, stage and
secret stable across redeploys to retain state, data and sessions.

AUTH_BASE_URL must be the exact public HTTPS origin. For a custom domain, set
WORKBASE_DOMAIN to its hostname, with no scheme/path, and use the same hostname
in AUTH_BASE_URL. The domain must be in a Cloudflare-managed zone in the account;
arrange DNS/domain access with the operator. `{stage}` in the URL/domain expands
to the SST stage. For workers.dev, determine the exact generated Worker hostname
before deployment; the packaged createProvisionPlan() returns its stable name.
An omitted domain does not arrange a login transport.

EMAIL_FROM is required by this starter. Authorize that sender through Cloudflare
Email Routing/send_email in the selected account/domain. provision() creates an
EMAIL send_email binding restricted to that address and an EMAIL_FROM variable.
Cloudflare delivery restrictions still apply: configure/verify the recipient when
required by the account's email setup, including WORKBASE_OWNER_EMAIL. A healthy
Worker alone does not prove mail delivery or login. Request a magic link over
HTTPS, follow it, create/select an organization, then verify console reads/writes.

SST 4.17.1 Cloudflare home uses the shared account-level R2 `sst-state` bucket.
Arrange access and an explicit state-sharing decision before deployment; an app
resource prefix does not isolate that bucket. Do not substitute local state.
The token needs the selected account's Worker, D1, KV, Queues and R2 state access,
plus the zone/domain and email permissions required by your chosen setup.

```sh
bun run deploy --stage production
# A disposable stage: use a lowercase DNS-style name <=32 characters.
bun run deploy --stage trial
bun run remove --stage trial
```

The thin sst.config.ts calls @workbasehq/core/infra/provision with
assetsDir: consoleAssetsDir() from @workbasehq/plugins/console/assets.
Packaged workbase-migrate applies/validates SQL and plugin ledgers before Worker
upload and binds SCHEMA_EXPECTED. D1, KV, queues/DLQ, consumer and relay cron are
owned by SST; production resources are protected/retained. An explicit manual
migration is available as `DATABASE_ID=<id> bun run migrate:remote` using the same
packaged command. Normal deploys already perform this step.

## CI/CD

Set repository/environment secrets CLOUDFLARE_API_TOKEN and BETTER_AUTH_SECRET.
Set variables CLOUDFLARE_DEFAULT_ACCOUNT_ID, WORKBASE_RESOURCE_PREFIX,
WORKBASE_STAGE_PREFIX, AUTH_BASE_URL, WORKBASE_DOMAIN (optional), EMAIL_FROM.
Configure `preview`, `staging` and `production` GitHub environments. Preview
URL/domain values can contain `{stage}`. Preview stage is `<WORKBASE_STAGE_PREFIX>-pr-N` (<=32 chars).
Use the same prefix and environment settings for deploy and cleanup.

CI installs the committed lockfile, generates SST types, typechecks and checks SQL.
Same-repository PRs deploy with SST after checking the PR is still open. Closing a
PR runs trusted main code and removes that preview stage. Deployment and cleanup
share serial concurrency. A push to main deploys Staging; workflow_dispatch can
also deploy Staging from main. Production runs only for tags matching `v*`.
Release with a tag `vX.Y.Z` on the commit already green on Staging. The release
guard resolves annotated tags to commits, requires that SHA to be reachable from
main and have a successful `staging.yml` push run on main, then deploys exactly
that SHA even if main has advanced. Manual Staging runs do not qualify as release
evidence. Verification uses only GITHUB_TOKEN with contents: read and actions: read.
CI cleanup rejects both Staging and Production; only PR previews may be removed.
Fork PRs run checks only. Cleanup authorization/network failures remain failures;
rerun when resolved.

Existing instances must update their workflows and scripts manually from this
template (including staging.yml and release-guard.ts). Bootstrap preserves
existing files and reports conflicts; it does not overwrite them or perform an
in-place upgrade.

SST logs its outputs. After deployment verify schema compatibility, console assets,
HTTPS magic-link login, organization creation and authorized writes. Real remote
acceptance and stage cleanup require operator credentials and account/state setup.
